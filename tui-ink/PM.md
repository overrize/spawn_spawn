# PM Spawn 决策规则与教训

> 本文档记录 PM spawn Tech Lead 的失败案例和决策规则，持续更新

## 一、Spawn 前置检查清单

**在发出 spawn 事件之前，PM 必须确认以下所有项：**

| # | 检查项 | 验证方法 |
|---|--------|----------|
| 1 | 工具链可达性 | 目标操作的外部服务/端点能否通过 Bash curl 访问？PM 必须先跑一条测试命令验证 |
| 2 | 任务性质匹配 | 确认任务类型在"适合 TL"列表中（见第二节）|
| 3 | Goal 闭合性 | Goal 是否能在有限步数内被明确判断为"完成"？是否定义了明确的验收标准？ |
| 4 | 不可控环节拆分 | 是否把"需要语义判断"的环节留在了 PM 侧？ |
| 5 | 备用策略 | dispatch 的 constraints 里是否包含了"如果方法A失败，立即切换方法B"？ |

---

## 二、任务类型适配表

| 任务类型 | 适合 TL？ | 原因 | 替代方案 |
|---|---|---|---|
| 代码实现/重构 | ✅ 适合 | 文件系统是全部输入输出 | 直接 spawn |
| 多文件分析与报告 | ✅ 适合（需PM先确认范围） | 静态代码，Grep/Read 能覆盖 | 先指定文件列表再 spawn |
| 运行测试/调试 | ✅ 适合 | Bash 能跑编译器/测试框架 | 直接 spawn |
| 格式转换/文档生成 | ✅ 适合 | 输入文件明确，输出可验证 | 直接 spawn |
| **实时 Web 检索/爬取** | ❌ 不适合 | 需要浏览器/API认证/反爬对策 | PM 用 API 先检索，筛选后交 TL 整理 |
| **语义筛选/质量判断** | ❌ 不适合 | 需要领域专业知识 | PM 自己的 LLM 判断，或交用户确认 |
| **需要 GUI 的操作** | ❌ 不适合 | 只有终端环境 | 告知用户手动操作 |
| **需登录/认证的服务** | ❌ 不适合 | 无凭证管理 | PM 手动完成认证后提供 token/文件 |
| **开放探索性研究** | ❌ 不适合 | 无收敛条件，死循环高风险 | 先由 PM 缩小范围到明确边界再 spawn |

## 三、Spawn Goal 编写规则

### 好的 Goal
```
"根据 docs/api-list.md 中列出的 8 个 API 端点，生成格式化的 API 文档 api-docs.md"
"扫描 src/ 下所有 .ts 文件中 TODO 注释，按优先级分类整理到 todo-report.md"
```
✅ 边界清晰、输入输出明确、可验证

### 坏的 Goal（曾导致 spawn 失败）
```
"检索并整理符合条件的论文"
"分析项目代码质量"
"优化系统性能"
```
❌ 输入不明确、判断标准主观、无限步数

### 规则
1. **Goal 必须是一句话能验收的边界**
2. **必须明确输入文件/数据源路径**
3. **必须明确输出文件路径和格式要求**
4. **如果输入需要从外部获取，PM 必须先获取并放到本地文件**

---

## 四、Dispatch Constraints 必须包含

每次 spawn 的 `dispatch.constraints` 必须包含：

1. **读写切换约束**：`"读完 N 个文件后必须开始产出，不得长期只读不写"`
2. **失败切换策略**：`"如果方法 A 在第 N 轮无结果，立即切换到方法 B"`
3. **输出阶段性要求**：`"每 X 轮必须写出中间产物到 <file>"`
4. **禁止行为清单**：如 `"禁止访问 scholar.google.com"`、`"禁止修改 src/ 外的文件"`

## 五、失败案例记录

### 案例 1：文献检索 spawn 连续两次失败（2025-12-03）

**任务**：检索"视频映射人体关节 DOF 到机器人"相关论文并整理

**Spawn 历史**：
- `tl-01`：3轮无有效行动，被 PM 检测卡住
- `tl-02`：同上，3轮无产出

**根因**：
1. **工具链不可达**：dispatch 指示用 scholar.google.com，但 TL 环境只有 Bash/curl，Scholar 有反爬机制，裸 curl 拿不到有效结果
2. **任务类型不适配**："筛选高相关论文"需要语义判断，TL 只能做关键词匹配
3. **Goal 过于开放**："检索并整理"无收敛条件、无指定数据源路径
4. **未提供备用策略**：没有在 constraints 里写"如果 Scholar 不可用，立即改用 arxiv API"

**教训应用**：
- 此后所有涉及 Web 检索的任务，PM 先用自己的 Bash 验证 API 可达性
- 语义筛选任务留在 PM 侧完成后，把确定列表交给 TL
- dispatch 必须包含失败切换策略
- spawn 前走完整前置检查清单

## 六、PM 自查（每次 spawn 前快速过一遍）

1. 我能用一条 `curl` 或 `Bash` 命令验证这个任务的关键步骤可达吗？
2. 这个任务有没有需要"专业判断"或"审美判断"的环节？有 → 留在 PM
3. TL 收到 goal 后，是不是能不问任何问题就直接开干？
4. 如果第一步就失败，TL 知道该换什么策略吗？

**4 个都 Yes → 可以 spawn。任何一个 No → 先修 goal 再 spawn。**

## 七、TL 存活性监控规则

spawn TL 后，PM 每 3 轮主动检查：
- 产出目录是否存在且非空
- 最近 5 分钟是否有新文件
- TL decisions 列表是否有"修改/创建文件"类记录（不能全是"读取"）

发现异常立即 message→user 汇报，不等用户问。

## 八、TL 完成后验证

收到 agent.done 后：
1. 对照原始验收标准逐条确认
2. 读输出文件验证内容质量
3. message→user 汇总结果（说结果，不转述技术细节）
4. todo.set 更新状态

## 九、问题记录：PM 空回复（多个 PM 标记、只有一个有内容）

**现象**：用户提问后出现多个 "PM:" 前缀，只有一个包含内容，其余为空或仅含时间戳。

**根因**：PM 在同一轮回复中输出了多行 JSON（例如 step 和 message 分成两行），系统将每一行都当作一次独立回复；格式不完整或非 message 类型的行被丢弃，但用户仍看到空的 PM 标记。

**应对措施**：
1. PM 必须严格遵守"每轮只输出一个紧凑单行 JSON"的协议约束
2. 所有需要传递的信息（step、message、tool.call 等）应合并到同一个 JSON 对象中
3. 如果用户发现空回复现象，可直接提醒 PM 检查输出格式
