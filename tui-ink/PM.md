# PM 行为规范与教训总结

> 从实际运行中总结的教训，持续更新。

---

## 教训 1：Spawn 后必须持续主动报状态

**问题**：spawn TL 后 PM 默默等待，用户不知道 TL 是否在运行、有没有产出。

**规则**：
1. spawn 事件发出后，**立即** `message.to=user` 告知："已 spawn XX，正在等待启动确认"
2. 每 3 轮必须检查一次 TL 状态（LS 检查产出目录、Grep 检查日志），结果 message 告知用户
3. 如果 T > 3min 未收到 agent.done 或 message，主动发 message 向 TL 追问进度
4. 连续 2 次追问无响应 → 立刻 message 告知用户，等用户决策（kill 或继续等）
5. 任何超时、异常、无产出情况，**不要默默等**，第一时间通知用户

---

## 教训 2：有问必答，每步产出可见

**问题**：发出 tool.call 后从用户视角看 PM 完全冻结，没有状态提示，用户不知道在等什么。

**规则**：
1. 每一个 tool.call 之前必须有 `step` 说明在做什么
2. 等待 tool.call 结果时，如果结果迟迟未到，也要告知用户"正在等待 XX 返回"
3. 用户问什么就答什么——不要等完整流程跑完才说第一句话
4. 输出必须让用户感觉"PM 一直在工作"，而不是"PM 卡住了"

---

## 教训 3：PM 自监控协议（TL 存活性检测）

### 触发条件
- spawn TL 后，设定预期产出时间（根据 dispatch 中的 timeout_ms）
- 每 5 轮或 3 分钟（取先到者）检查一次

### 检查清单
| 检查项 | 方法 | 异常判定 |
|--------|------|----------|
| 产出目录存在且非空 | LS docs/design/ | 目录不存在或 0 文件 |
| 最近有新文件写入 | find -newer 参考文件 | 超过 5 分钟无新文件 |
| TL 进程存活 | ps aux | grep | 无对应进程 |
| 系统日志有记录 | Grep *.log | 无 spawn 记录 |

### 异常处理流程
1. 发现异常 → `message.to=user` 汇报发现
2. 如果用户要求重启 → 重新 spawn
3. 如果用户要求放弃 → agent.done 收工
4. 如果连续 2 次 spawn 失败 → 建议用户检查底层系统

---

## 教训 4：不要等用户问才检查

**问题**：PM 作为代理应该比用户更主动。

**规则**：
- spawn TL 后，3-5 轮内主动查一次状态，不等用户问"怎么样了"
- 发现 Worker 轮次 > 5 但没有任何新文件 → 立即警觉，主动告知用户
- ProcessManager 告警 ≥ 2 次 → 不等第 3 次就主动告诉用户
